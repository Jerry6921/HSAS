## 1. 用户明确决定

本文件沿用总文档的 U（用户决定）、D（必要推导）、P（设计建议）、E（现状证据）状态区分。

| ID | 已确认内容 | 对话依据 |
| --- | --- | --- |
| EN-U-01 | 根据用户需求和课程 syllabus，通过 SIS Information 查询课程信息，协助规划课程或安排课表。 | 用户提出的第二个功能。 |
| EN-U-02 | 排课与自动抢课／enrol 结合。单个目标失败后生成下一方案，再执行，持续推进至全部目标完成 enrol。 | “单一抢课失败后会生成第二计划，并再次执行，直到所有课都完成enrol” |
| EN-U-03 | 可以在事先认可的课程候选池内自动换课、换班或换时段。 | 用户选择“在事先认可的课程候选池内换课、换班或换时段”。 |
| EN-U-04 | 已成功 enrol 的课程保持不变，只调整尚未成功的目标。 | 用户选择“保留已成功 enrol 的课程，只调整尚未成功的目标”。 |

“抢课”是用户表达的自动选课目标；产品执行需识别实际课程采用的选课与审批机制。不能默认所有课程都通过重复提交即可获批。

## 2. 一个完整用户流程

1. **理解要求**：解析学期、课程／学分目标、必选课程、兴趣方向、时间限制和偏好，以及用户同意的替代范围。
2. **查询与核对**：读取课程 syllabus、适用的 SIS 课程资料、课程开设及班别安排，并结合已修和已选课程判断可行性。
3. **形成候选池**：说明推荐依据、可替代关系、优先级、限制和未知项。已有明确候选池时直接复用；新增候选池需先取得认可。
4. **生成首选方案**：满足硬约束，再按用户偏好排序；为可能失败的目标保留可行替代路径。
5. **执行与核验**：在已授权学期、时间窗口及候选池内执行 enrol，读取逐项结果并回查真实状态。
6. **根据结果重新规划**：固定已成功课程，刷新变化的信息，为剩余目标生成与当前已选课表兼容的下一方案并执行。
7. **完成或准确等待**：全部目标获确认时交付最终课表；暂时无可执行动作时保留目标、原因及恢复条件。

规划、排课、执行属于同一用户体验中的三个能力层次；是否拆成多个 Skills、服务或工具属于后续架构决定（P），不是当前指定的目录结构。

## 3. 输入与完成条件

### 3.1 规划输入（D）

- 学术身份：适用的课程、学期与计划范围。若涉及毕业路径，则还需要入学年份对应的 programme curriculum／regulations、已修、豁免和剩余要求；单门课 syllabus 不能独立证明满足整个学位要求。
- 课程信息：课程代码、学分、内容、先修／共修／互斥要求、开设学期与适用学生限制；缺失字段保持未知。
- 课表信息：具体班别、Lecture／Tutorial／Lab 等关联组件、日期与周次、时间、地点及可验证的组合规则。
- 用户目标：必选项、可替代目标、目标课程数或学分、已认可候选池和优先级。
- 偏好：例如尽量集中上课、避开早课或保留某天。将硬约束与可以让步的软偏好分开记录。
- 执行信息：当前已 enrol 状态、开放窗口、实时可选状态、必要审批状态，以及用户授权的任务范围和有效期。

能从当前资料解析的内容无需重复询问。单学期规划与跨学期学业规划的具体范围在实际请求中确定；自动 enrol 只执行当时已授权且实际开放的学期目标。

### 3.2 “所有课完成”的含义（D）

候选池不是全部都要 enrol 的课程清单。例如目标 G1 是“课程 A 或 B 二选一”，B 作为替代成功后只完成 G1 一次，不继续 enrol A，也不把两门课重复计入目标学分。

每个目标应能说明：必选课程或允许的等价候选、所需组件及学分贡献。成功条件是所有目标由已核验的正式 enrol 状态满足，同时课表和学分约束成立。

重新规划不能通过静默删除必选项、减少所需学分或把任意候选声明为等价来宣布完成。若目标只有精确课程而没有被认可的替代，该目标失败后仍须保留。

### 3.3 目标持续性与运行停止（D）

保留用户“直到所有课完成 enrol”的目标。实际执行遇到没有名额、窗口未开放或等待学院审批时，可进入等待；候选池与约束无解、窗口已结束、授权失效或用户取消时，准确报告阻塞／终止原因和未完成目标。

这些状态都不等于任务成功。系统不能保证学校释放名额或给予批准，也不能把持续重试等同于必然成功。恢复条件、检查频率和执行有效期应属于明确的执行任务配置，不能无限高频循环或在失去授权后继续提交。

## 4. 课程查询与排课要求

### EN-F-01：查询候选课程，而不局限于已 enrol 课程（D）

支持用户候选和规划范围中的未选课程。保存来源、适用学期、取得时间及相关版本；区分课程说明、programme 要求、班别安排、实时名额和用户执行状态。

课程内容与考核信息可参考 syllabus；注册规则、开放窗口和 enrol 结果由对应官方来源核对。不能把仅适用于已选课程采集的流程直接当作完整课程发现能力。

### EN-F-02：显式区分约束与偏好（D）

先检查已知的资格、课程关系、学分与时间硬约束，再优化软偏好。未知资格不能静默视为满足。多门课同时失败时，重新求解剩余整体组合，而非逐门选择导致新的冲突。

时间冲突检查基于实际日期、周次与全部必要组件；有官方考试时间时一并考虑，缺失时标明未检查。用户要求的交通缓冲等按用户设定应用，不预设所有学生都需要相同参数。

### EN-F-03：方案可解释、可重建（D）

方案记录所用输入快照、课程／班别身份、约束、优先级与选择理由。下一方案说明失败原因、变化项目及仍保持的要求。可以预先保留备选，也应支持基于新结果动态生成，而不只机械切换静态 A／B。

## 5. 自动执行与重试要求

### EN-F-04：授权以任务和候选池为单位（EN-U-03，D）

未来真实 enrol 任务在确认账户、学期、目标、候选池和执行范围后，可以在该范围内自动提交及重试，无需每次换候选或重试都重新询问。扩展候选池或改变硬约束需要新的用户决定。

本轮是功能设计与文档更新，不构成向当前账户提交真实选课操作的指令。

### EN-F-05：固定已成功课程（EN-U-04）

以最新实际 enrol 状态构造固定集合。方案不能 drop、swap 或改变其已成功的班别／时段来优化剩余课表。无解时报告冲突，而不是先退已成功课程再尝试新课。

对待审批请求、候补和结果未知的提交单独保存；它们既不直接算作已成功，也不自动被当成失败撤销。若需要撤销这些请求才能推进，需根据实际任务的明确权限处理，当前尚未确认该权限。

### EN-F-06：逐项读回并处理结果未知（D）

保存一次提交的目标、方案版本、尝试标识、时间及结果。提交后按课程与所有必要组件核验，不能仅凭按钮点击、HTTP 成功或页面跳转判定成功。

网络超时、浏览器崩溃等可能发生在学校已接受提交之后。此时先查询实际状态并对账，再决定是否重试。并发运行或用户手动修改后重新读取当前状态，避免重复提交已完成目标或用旧方案覆盖新状态。

### EN-F-07：按失败原因处理（D）

| 观察结果 | 行为 | 对目标的影响 |
| --- | --- | --- |
| 名额已满／班别关闭 | 在候选池内重新规划；无立即可行候选时等待相关状态变化。 | 目标未完成，保留未来恢复条件。 |
| 排课冲突 | 固定已成功课程，重新安排剩余课程及组件。 | 不放弃硬约束。 |
| 先修、学生类别或学分限制 | 核验原因，排除当前不可行组合或等待必要审批。 | 条件未变化前不重复提交相同无效组合。 |
| Pending／等待审批／适用的候补状态 | 保存申请并核对对应流程，等待决定。 | 不计入最终成功，也不立即作为失败重投。 |
| 请求超时／结果未知 | 先查实际状态。 | 已完成则跳过；确认为未完成后再重试。 |
| 临时服务故障／限流 | 保存状态，按来源反馈与适度退避恢复。 | 不把临时错误解释成课程不合资格。 |
| 登录失效／需要用户完成认证 | 暂停提交，保留方案与进度，要求必要的认证动作。 | 认证恢复后先对账再继续。 |
| 所有候选不可行／窗口已关闭 | 明确阻塞原因、已成功项及未完成目标。 | 保留未完成事实，不虚构可执行方案。 |

退避、检查间隔和对未知状态的重试次数由架构方案结合实际服务能力制定（P），不在本文硬编码秒数。用户持续推进的目标与单次运行的资源预算分别处理；预算耗尽时保留恢复点。

### EN-F-08：完成核验与交付（D）

读取真实 enrol／approval 状态，核对目标、组件、学分与课表。交付实际成功课表、最终选课清单、采用的替代关系，以及仍在等待或阻塞的项目和原因。计划课表与实际课表明确区分。

若学校后续审批改变结果，应能在任务约定的有效期内重新对账并恢复未完成目标；本轮未要求无限期监控所有历史 enrol。

## 6. 状态设计要求

以下是语义要求，状态名及持久化格式是建议（P），不作为既定 API：

| 任务状态 | 含义 | 后续 |
| --- | --- | --- |
| planning | 查询资料与构建可行方案。 | 得到当前可执行计划或说明无解。 |
| executing | 在授权范围提交尚未成功的目标。 | 逐项核验。 |
| reconciling | 对提交结果、外部修改或恢复后的实际状态进行核对。 | 更新成功集合，再决定执行或重新规划。 |
| replanning | 固定成功集合，为剩余目标生成新计划。 | 可行则执行，否则等待或阻塞。 |
| waiting | 等待名额、开放窗口、服务恢复或审批。 | 记录等待条件与下一次实际检查机制。 |
| needs-user | 缺少认证、必要决定或新增授权。 | 只请求需要的信息，保留现有进度。 |
| blocked | 当前已知条件下无法完成，说明原因。 | 条件改变后可恢复。 |
| completed | 所有目标经官方状态核验满足。 | 输出最终成果。 |
| cancelled | 用户取消或授权终止。 | 停止后续提交，保留结果；不自动退课。 |

课程级结果与任务级状态分开，保留学校原始状态与可读说明。`waiting` 或 `blocked` 不能通过改名为 completed 隐藏剩余目标。声称“持续运行”时须存在实际可运行的执行器；会话结束后的恢复机制需要独立验证。

## 7. 已核对的官方流程事实

以下仅说明规则设计依据，核对日期为 2026-10-17；具体学生、课程和时段仍需执行时核验。

- HKU AAS 说明 Pending 表示等待审批，且课程可采用先到先得、系统抽签或人工抽签；加退选期后需按特殊审批流程处理。来源：[SIS FAQ，Q6.2–Q6.8、Q6.11](https://aas.hku.hk/faq/faq06-sis/)。
- 工程学院 FAQ 的 Q10–Q11 说明满额时可留意释放名额，Pending 与 Approved 不同。该 FAQ 的其他学分或课程示例不能不经核对地套用于所有入学年份。来源：[Engineering UG FAQ](https://engg.hku.hk/Portals/0/UG/FAQs.pdf)。
- 2026 年 Common Core 通知对选课期与加退选期采用不同审批方式，并说明待批请求可能在期末清除。此为特定课程类别和时段的证据。来源：[2026-08-19 Common Core 通知](https://commoncore.hku.hk/2026/08/19/important-to-year-1-students-approval-on-common-core-enrollments-during-course-selection-period/)。

由此推导：执行器需要处理“暂存／已提交／待审批／最终获批”等阶段，并按实际来源映射；不能把整个流程简化为不断点击 enrol。

## 9. 验收场景

| ID | 场景 | 通过依据 |

| EN-AC-04 | 多个目标或关联 Tutorial／Lab 失败。 | 重新求解剩余整体组合，完整组件与日期／周次不冲突。 |

| EN-AC-07 | SIS 返回 Pending 或抽签处理中。 | 保存并等待，不标完成，不把其当作普通失败不断重新提交。 |
| EN-AC-08 | 提交超时，但学校已接受。 | 先回查对账，识别已成功或待批状态，不重复提交。 |
| EN-AC-09 | 先修或学分限制不满足。 | 解释来源与限制，不在条件不变时循环提交同一无效请求。 |
| EN-AC-10 | 会话过期、进程中断或服务暂不可用。 | 保留进度；恢复后读取实际状态再推进，无虚假后台运行报告。 |
| EN-AC-11 | 用户手动修改 SIS 状态或另一执行器同时运行。 | 识别新状态，更新固定集合，避免并发重复操作及陈旧方案执行。 |
| EN-AC-12 | 全池满额、审批未决或选课窗口结束。 | 报告已成功、待处理和无法完成的目标；保留恢复条件，不把任务标成全部完成。 |
| EN-AC-13 | 所有目标正式获批，且所有组件与学分约束满足。 | 回读核验后完成，最终实际课表与结果清单一致。 |
| EN-AC-14 | 用户取消任务。 | 停止后续提交，报告取消前已完成结果，不自动 drop 已选课程。 |

## 10. 架构接手任务与待决项

先提交最小架构方案，覆盖候选查询、约束表达、方案版本、逐项执行、结果核验、失败分类、恢复和完成判定。MCP／UI／CLI 使用同一应用边界，执行状态与 canonical 课程事实分开；具体模型和接口待设计。

需要在实际任务或架构核验中确定：

1. 学业规划范围、适用 syllabus／programme 年份及用户已修资料的取得方式。
2. 目标课程组、等价替代、硬约束和偏好排序；候选池已有明确认可时无需再次询问。
3. 提交、待审批及正式 enrol 状态的具体界面／合同，以及该课程类别的审批机制。
4. 任务运行窗口、授权有效期、检查与重试机制、会话结束后的实际执行或恢复方式。
5. 待审批／候补请求的保留与撤销策略；当前只确认了成功课程保持不变。
